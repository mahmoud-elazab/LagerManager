Phase 3, Step 6: Login REST API

Implementation
- Added AuthController exposing POST /api/auth/login with JSON email and password input.
- Added LoginRequest DTO with no-argument/full constructors and getters/setters, following existing DTO conventions.
- Added LoginResponse DTO containing only token and tokenType (Bearer).
- Extended AuthenticationService with constructor-injected UserRepository and JwtService. login() reuses authenticate(), retrieves the entity by the authenticated principal name, and calls JwtService.generateToken(). Spring Security continues to verify passwords and account status.
- Successful login returns HTTP 200 with the signed JWT and Bearer token type.
- Incorrect passwords, unknown users, and disabled accounts return the same generic HTTP 401 response. Missing/blank credentials, missing bodies, malformed JSON, and invalid body structures return generic HTTP 400 responses. Exception handlers are scoped to AuthController and do not return exception details or supplied input.
- No user creation, JWT filters, role restrictions, Lombok, or Git commands. JwtService and SecurityConfig unchanged; existing CRUD access remains unchanged.

Tests
Added AuthControllerTests using standalone MockMvc, a mocked UserRepository, and the real configured authentication provider, BCrypt encoder, AuthenticationService, and JwtService. Keys are generated ephemerally for tests. No test users are persisted.
- Successful login returns a JWT that verifies and identifies the authenticated user, with Bearer type and no password fields.
- Incorrect password, unknown email, and disabled account return generic 401 without a token.
- Thirteen invalid-request cases return generic 400 without consulting the repository: missing fields, null fields, empty/whitespace fields, empty body, JSON null, malformed JSON, and array body.
Updated existing authentication unit-test setup for the service's additional dependencies.
